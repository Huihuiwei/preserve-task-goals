# 每轮对齐与实质完成

在多轮任务、新增工作分支、用户怀疑“只做了皮毛”，或暂停后恢复时使用。这个流程帮助完成原任务，不要求每轮向用户交付表格或执行全部测试。

## 保留可追溯的目标

保留最初用户确认的目标、不可丢失的必需项和后续明确批准的变更。原目标可以由用户修改；“保持目标”不意味着忽略新的明确要求。助手摘要用于定位来源，不能替代来源。

每轮对照当前有效目标，而不是只与上轮计划一致：

1. 本轮用户是在补充要求、修正错误、询问状态，还是明确改变目标、暂停或限制操作？
2. 当前行动对应哪个必需项？实现对象、方法含义、输入输出和验收口径是否仍吻合？
3. 本轮实际补齐什么？哪些必需内容尚缺实现、接入或证据？
4. 接下来可执行的必需项是什么？若要停止，依据是用户边界、真实阻碍还是已满足验收？

若必须保存跨轮信息，更新已有记录中的目标来源、必需项状态和下一步即可。不要每轮重写基准，或把“完成了本轮计划”当作“完成了用户任务”。

## 判断新增工作是否服务于目标

| 新增工作的性质 | 如何判断与处理 |
| --- | --- |
| 完成原要求的必要实现步骤 | 能指出对应必需项及缺少它造成的具体缺口，在原授权内执行 |
| 排除实际阻碍或直接验证风险 | 能指出阻碍和依赖关系，完成针对性的排查或验证后返回主线 |
| 可能有益的额外功能、实验或美化 | 对原任务有益不等于必需；仅作为建议，未获批准不执行、不阻塞原任务 |
| 方法替换、机制删减、口径或验收变动 | 即使看似更高效或仍与主题相关，也属于需要明确批准的变更 |

不要把每个普通实现细节都变成审批事项，也不要用牵强的“间接相关”让所有新增内容合法化。判断与原目标的关系时，明确具体作用，而不是只复述主题名称。

## 分别核验四个方面

| 核验方面 | 要回答的问题 | 不能替代它的东西 |
| --- | --- | --- |
| 方向一致 | 当前工作是否解决用户确认的问题，遵守方法和口径？ | 与助手自己改写的计划一致 |
| 覆盖完整 | 全部必需功能、场景和交付是否仍被保留并逐项实现？ | 把多个关键要求合并为一个勾选项 |
| 实质实现 | 必需机制是否在实际调用路径中产生预期作用，结果是否到达最终使用位置？ | 函数名、参数声明、按钮、空壳模块、固定结果 |
| 证据充分 | 当前版本在约定条件下是否经过能发现相关错误的验证？ | 文件存在、无异常退出、旧日志或由同一实现生成的答案 |

对关键能力，从实际入口沿“输入 → 必需处理/状态 → 输出 → 下游使用”检查。按任务选择有效输入变化、机制干预、独立已知答案、适用边界或失败案例。不要求所有能力套用同一种测试；不存在明确预期时不凭直觉添加单调性或收益要求。

例如，用户要求带校准系数的报警工具：界面显示了系数并不够。必须核对用户设置进入真实计算、阈值作用于约定的量、报警结果进入最终输出，以及测试能发现系数被忽略的错误。该例只说明核验方法，不给其他项目增加校准或报警需求。

文档任务也检查实际内容：有章节标题不代表论证已经写出，有参考文献列表不代表论述获得支持。按原要求核验内容和交付，不能只数文件、标题或字数。

## 暂停、批准变更与恢复

- 用户要求“只读检查”时，交付审查发现；不以持续执行为由修改文件或运行被禁止的命令。审查可完成，而被审实现仍未完成。
- 用户说“先停下，等我继续”时，停止被暂停的操作，保留剩余要求。不能用旧的完整交付授权覆盖新暂停要求。
- 用户恢复执行后，核实当前文件与阻碍；缺失数据已经到位时，按原要求继续使用它，不沿用过期的“受阻”状态。
- 用户明确将 JSON 输出改为 CSV 时，只更新输出要求；未被改变的计算、错误处理和验证仍需完成。询问“增加图表会不会更好”只需要回答建议，不等于批准制作图表。
- 对正在运行的任务记录可继续观察的状态；不能把提交执行、请求受理或“我会继续”写成已经完成。工具无法继续观察时，说明真实限制，不虚构后台工作。

每轮核对不意味着每轮全量验收。实现变化后验证直接受影响的要求；交付前汇总当前有效证据覆盖原任务，仍可执行的缺项回到执行。
